# 架構設計

## 系統架構概觀

本專案採用**分層架構（Layered Architecture）**搭配**管線模式（Pipeline Pattern）**，由上而下分為四層：

```
┌─────────────────────────────────┐
│          使用者介面層             │  examples/ (CLI, Streamlit)
├─────────────────────────────────┤
│          主控制層                │  src/agent.py (DeepSearchAgent)
├─────────────────────────────────┤
│          處理節點層              │  src/nodes/ (各 Node 實作)
├──────────┬──────────────────────┤
│  LLM 層  │    工具層 / 狀態層    │  src/llms/ │ src/tools/, src/state/
└──────────┴──────────────────────┘
```

## 核心研究流程

```
使用者查詢
    │
    ▼
[1] ReportStructureNode ── LLM 產生報告大綱（最多 5 段落）
    │
    ▼
[2] 遍歷每個段落 ─────────────────────────┐
    │                                      │
    ├─ [2.a] FirstSearchNode ── LLM 產生搜尋查詢
    │       │
    │       ▼
    │    Tavily Search ── 執行網路搜尋
    │       │
    │       ▼
    ├─ [2.b] FirstSummaryNode ── LLM 依搜尋結果撰寫初稿
    │       │
    │       ▼
    ├─ [2.c] 反思迴圈（max_reflections 次）─┐
    │       │                               │
    │       ├─ ReflectionNode ── LLM 反思遺漏，產生新查詢
    │       │       │
    │       │       ▼
    │       │    Tavily Search
    │       │       │
    │       │       ▼
    │       ├─ ReflectionSummaryNode ── LLM 豐富段落內容
    │       │       │
    │       │       ▼
    │       └───── 回到反思迴圈頂端 ────────┘
    │
    ▼ （所有段落完成）
[3] ReportFormattingNode ── LLM 整合所有段落為最終 Markdown 報告
    │
    ▼
[4] 儲存報告 & 狀態
```

## 資料流圖

### 單一段落的資料流

```
paragraph.title + paragraph.content
        │
        ▼
  FirstSearchNode.run()
        │ 回傳 {search_query, reasoning}
        ▼
  tavily_search(search_query)
        │ 回傳 [{title, url, content, score}, ...]
        ▼
  paragraph.research.add_search_results()  ← 寫入狀態
        │
        ▼
  FirstSummaryNode.mutate_state()
        │ LLM 產生摘要 → paragraph.research.latest_summary
        ▼
  ┌─ ReflectionNode.run()
  │     │ 回傳 {search_query, reasoning}
  │     ▼
  │  tavily_search(search_query)
  │     │
  │     ▼
  │  paragraph.research.add_search_results()
  │     │
  │     ▼
  │  ReflectionSummaryNode.mutate_state()
  │     │ 更新 paragraph.research.latest_summary
  │     │ 遞增 paragraph.research.reflection_iteration
  └─────┘ （重複 max_reflections 次）
```

## 設計模式分析

### 1. 策略模式（Strategy Pattern）— LLM 抽象

```
BaseLLM (ABC)
├── invoke(system_prompt, user_prompt) → str
├── get_default_model() → str
└── validate_response(response) → str

DeepSeekLLM(BaseLLM)    OpenAILLM(BaseLLM)
```

`DeepSearchAgent` 透過 `config.default_llm_provider` 決定使用哪個實作，執行時期多型切換。

### 2. 範本方法模式（Template Method）— 節點

```
BaseNode (ABC)
├── run(input_data) → Any          [抽象]
├── validate_input(input_data)     [可覆寫]
├── process_output(output)         [可覆寫]
└── log_info() / log_error()

StateMutationNode(BaseNode)
└── mutate_state(input_data, state) → State  [抽象]
```

所有節點遵循相同的 `run → process_output` 流程，差異在具體 Prompt 與輸出處理。

### 3. 資料類別模式（Data Class）— 狀態管理

使用 Python `dataclasses` 實作，每個類別都提供 `to_dict()` / `from_dict()` 雙向序列化。整個 `State` 可透過 `save_to_file()` / `load_from_file()` 持久化為 JSON。

### 4. 管線模式（Pipeline Pattern）— 研究流程

`DeepSearchAgent.research()` 方法中，各步驟依序串接，每個步驟的輸出成為下一步的輸入。雖然不是顯式的管線物件，但邏輯上形成清晰的 Pipeline。

## LLM 呼叫策略

所有 LLM 互動都採用 **system prompt + user prompt** 的二訊息結構：

| 節點 | System Prompt 常數 | 輸入格式 | 輸出格式 |
|------|-------------------|----------|----------|
| ReportStructureNode | `SYSTEM_PROMPT_REPORT_STRUCTURE` | 查詢字串 | JSON Array `[{title, content}]` |
| FirstSearchNode | `SYSTEM_PROMPT_FIRST_SEARCH` | JSON `{title, content}` | JSON `{search_query, reasoning}` |
| FirstSummaryNode | `SYSTEM_PROMPT_FIRST_SUMMARY` | JSON `{title, content, search_query, search_results}` | JSON `{paragraph_latest_state}` |
| ReflectionNode | `SYSTEM_PROMPT_REFLECTION` | JSON `{title, content, paragraph_latest_state}` | JSON `{search_query, reasoning}` |
| ReflectionSummaryNode | `SYSTEM_PROMPT_REFLECTION_SUMMARY` | JSON `{title, content, search_query, search_results, paragraph_latest_state}` | JSON `{updated_paragraph_latest_state}` |
| ReportFormattingNode | `SYSTEM_PROMPT_REPORT_FORMATTING` | JSON Array `[{title, paragraph_latest_state}]` | Markdown 文字 |

每個 Prompt 都在 System Prompt 中嵌入了對應的 JSON Schema 定義，引導 LLM 輸出結構化資料。

## 容錯機制

1. **JSON 解析失敗時的多層回退**：
   - 先嘗試 `json.loads()`
   - 失敗則用 `extract_clean_response()` 以正則提取 `{...}` 或 `[...]`
   - 仍失敗則使用預設值（如預設搜尋查詢、預設報告結構）

2. **報告格式化備用方案**：
   - `ReportFormattingNode.run()` 失敗時，自動切換到 `format_report_manually()` 手動拼接 Markdown

3. **搜尋失敗**：
   - `tavily_search()` 捕獲所有例外並回傳空清單，不會中斷研究流程
